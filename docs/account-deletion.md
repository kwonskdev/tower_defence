# 계정 삭제와 보관 기간 자동 정리 (#66)

멀티플레이 출시용 개인정보처리방침 초안(`docs/multiplayer-release-privacy-policy.html`, PR #65)이 약속하는 보관/삭제를 **서비스(`tools/accounts/accounts_service.py`)가 실제로 하게** 한 작업이다. 방침 문서는 건드리지 않았고, 서비스를 방침에 맞췄다.

## 1. 방침 문구와 실제 동작

| 방침(3절 보유 기간, 6~7절) | 서비스 동작 | 어디서 확인 |
|---|---|---|
| 계정(계정 ID, 토큰 해시, 닉네임, 접속/변경 시각)은 **마지막 접속 후 365일**이 지나면 삭제 | 서비스가 켜질 때 한 번, 그 뒤 24시간마다 스스로 `purge`를 돈다 (`--inactive-days 365`). 차단 계정도 같다 | `test_account_deletion.py` `PurgeTest`, `RetentionJobTest`, `ServiceProcessTest`(실제 서비스 프로세스) |
| **판 기록은 계정과 함께 삭제**, 별도 보관 없음 | 계정이 지워지면 그 계정의 판 기록도 지운다 (아래 2절). 판 기록에 따로 보관 기간을 두지 않는다 (`--match-days`는 없앴다) | `DeleteAccountTest`, `tests/test_accounts.gd` [8] |
| 삭제를 요청하면 **요청 후 30일 이내** 삭제 | 운영자가 `delete-account` 명령으로 처리한다 (아래 4절). 메일 확인부터 삭제까지 30일 안에 하는 것은 **운영 절차**다 | `CliTest` |
| 서버 로그는 **30일** 후 삭제 | 같은 정기 작업이 `logs\`의 30일 지난 `*.log`를 지운다 (`--log-dir`, `--log-days 30`) | `RetentionJobTest` |
| 백업은 매일, 최근 **14개**만 남겨 삭제된 정보가 **최대 14일** 안에 사라진다 | 이미 그렇게 동작한다 (`--backup-interval-hours 24 --backup-keep 14`). 삭제가 백업에서 사라지는 것은 사본이 순환될 때다. **수동으로 `backup`을 자주 하면 14개가 더 빨리 순환한다(더 짧아질 뿐 길어지지 않는다)**. 백업 폴더를 OneDrive 같은 동기화 폴더에 두면 그쪽의 휴지통/버전 기록은 이 서비스가 지울 수 없다 | `docs/accounts-and-db.md` 8절 |
| 삭제는 데이터베이스에서 삭제 | 지운 글자가 SQLite 빈 페이지에 남지 않게 `secure_delete`로 0으로 덮어쓴다 | `test_deleted_text_is_really_gone_from_the_database_file` (DB 파일을 직접 읽어 확인) |

**소유자 결정(코디네이터가 답하지 못해 작업자가 추천안으로 정한 것, 바꾸려면 알려 달라)**

1. 다인원 판에서 한 명이 삭제되면: 그 사람의 줄만 익명(`(삭제된 사용자)`, 계정 연결 끊김, 피해량 등 숫자는 유지). 방(팀) 기록은 **계정이 연결된 참가자가 한 명이라도 남아 있는 동안** 유지하고, 마지막 한 명까지 지워지면 판 전체(게스트 줄 포함)를 삭제한다.
2. 자동 정리는 **서비스 내부 타이머** (작업 스케줄러 등록 없음).
3. 차단 계정도 365일 뒤 삭제한다 (방침에 예외 문구가 없어서). 차단 기록을 더 오래 두려면 방침에 예외를 적어야 한다.
4. 로그 30일 삭제도 같은 정기 작업에 넣었다.

## 2. 삭제하면 판 기록은 어떻게 되나

한 판(`matches`)에는 참가자 줄(`match_players`)이 여러 개 있다. 계정 하나를 지울 때:

| 상황 | 결과 |
|---|---|
| 그 계정이 낀 판에 **계정이 연결된 다른 참가자가 있다** | 그 계정의 줄만 닉네임을 `(삭제된 사용자)`로 바꾸고 계정 연결을 끊는다. 판(방 기록)과 다른 참가자 줄은 그대로. 순위에는 남는다 |
| 그 계정이 **마지막으로 남은 계정 참가자**다 (혼자 한 판 포함) | 판 전체를 삭제한다. 그 판의 게스트 줄(닉네임 글자)도 같이 사라진다 |
| 계정이 하나도 없는 판 (전원 게스트) | **저장하지 않는다**. 지워 줄 계정이 없어 영원히 남게 되기 때문이다 (게스트 닉네임은 판 기록과 함께 저장되므로). 이전 버전이 저장한 것은 정리 때 지운다 |
| 계정이 삭제된 뒤 방 서버 대기열에서 **늦게 도착한** 판 기록 | 그 계정 줄은 처음부터 익명으로 저장한다 (닉네임이 되살아나지 않는다). 남은 계정이 없으면 저장하지 않는다 |

삭제 뒤에도 같은 토큰으로 접속하면 **새 계정**이 만들어진다 (삭제를 요청한 사람은 앱을 지우라고 안내한다).

방 서버(Godot)는 순위 조회 결과를 30초 캐시한다. 삭제 직후 최대 30초까지는 서버 캐시에 이전 순위가 남을 수 있다 (서비스 DB에서는 이미 사라졌다).

## 3. 자동 정리 (365일 계정, 30일 로그)

`run-accounts.ps1`이 서비스를 띄울 때 `deploy\windows\settings.ps1`의 값을 넘긴다. 서비스는 **켜질 때 한 번**(서비스가 꺼져 있던 동안 밀린 정리를 따라잡는다), 그 뒤 **24시간마다** 다음을 한다:

1. 마지막 접속(`last_seen_at`)이 365일 지난 계정을 판 기록 처리(2절)와 함께 삭제
2. 어느 계정과도 이어지지 않은 판 기록 삭제
3. `LogDir`(기본 `logs\`)에서 마지막 수정이 30일 지난 `*.log` 삭제

| 설정 (`settings.ps1`) | 기본 | 서비스 옵션 |
|---|---|---|
| `AccountsPurgeHours` | 24 (0이면 자동 정리 끔: 끄면 방침과 어긋난다) | `--purge-interval-hours` |
| `AccountsInactiveDays` | 365 | `--inactive-days` |
| `LogRetentionDays` | 30 | `--log-days` (`--log-dir`은 스크립트가 `LogDir`로 채운다) |

- 작업 결과는 서비스 로그(`logs\accounts-*.log`)에 한 줄 **개수만** 남는다: `보관 기간 정리: {"players": 1, "matches_deleted": 1, "matches_anonymized": 0, "logs": 3}`. 삭제된 계정의 ID/닉네임은 로그에 남기지 않는다. **이 줄이 매일 보이는지 보면 자동 정리가 도는지 알 수 있다.**
- 정리가 실패하면 `보관 기간 정리 실패:` 가 로그에 남고 서비스는 계속 돈다 (다음 주기에 다시 한다).
- 서비스 없이 한 번 돌리기: `python tools\accounts\accounts_service.py --db data\accounts.db purge --log-dir logs` (서비스가 떠 있어도 된다).
- 작업 스케줄러가 아니라 서비스 안의 타이머이므로 `install-autostart.ps1`을 바꾸지 않았다. 서비스가 계속 꺼져 있으면 정리도 안 된다 (자동 시작으로 켜지게 이미 되어 있다).
- 서비스 로그가 직접 `*.log` 파일을 쓰는 중이어서 지워지지 않으면(`로그 삭제 실패:`) 다음 주기에 다시 시도한다.

## 4. 삭제 요청 처리 절차 (운영자)

방침 6절: 이용자는 앱 메뉴의 **[데이터 삭제 요청]**(메일 링크)로 `nerochaos1@gmail.com` 에 "데이터 삭제 요청"과 **닉네임**을 적어 보낸다. 운영자는 **30일 이내**에 처리한다.

1. **요청 받기**: 메일에 닉네임과 "접속한 대략의 시기"가 있는지 본다. 없으면 답장으로 묻는다 (방침 6절의 본인 확인 문구).
2. **계정 찾기와 본인 확인**: 서버 PC에서
   ```
   python tools\accounts\accounts_service.py --db data\accounts.db show <닉네임 또는 계정 ID>
   ```
   `만든 시각`, `마지막 접속`, `판 수`, `마지막 판 시각`이 나온다 (토큰 해시는 안 나온다). 메일이 말한 시기와 맞는지 비교한다.
   - 익명 계정이라 이메일 주소와 계정을 직접 이을 방법이 없다. **본인 확인은 닉네임 + 대략의 접속 시기 + (가능하면) 메일에 적힌 판 기록 내용이 맞는지**로 한다. 이 확인이 약하다는 것이 이 방식의 한계이고, 요청이 모호하거나 다른 사람 계정을 지우려는 것으로 보이면 지우지 말고 답장으로 더 묻는다.
   - 닉네임이 없다는 결과가 나오면 앱을 이미 지웠거나 닉네임을 바꾼 경우다. 이전 닉네임/시기를 묻는다. 앱을 지운 뒤에는 같은 계정임을 확인하기 어렵다고 방침이 밝히고 있다.
3. **미리보기** (아무것도 지우지 않는다):
   ```
   python tools\accounts\accounts_service.py --db data\accounts.db delete-account <계정 ID>
   ```
   지워질 판 수와 익명 처리될 판 수가 나오고 종료 코드 2로 끝난다.
4. **삭제**: 같은 명령에 `--yes`를 붙인다. 닉네임보다 **계정 ID**를 쓰는 것이 안전하다.
   ```
   python tools\accounts\accounts_service.py --db data\accounts.db delete-account <계정 ID> --yes
   ```
   `{"id": ..., "matches_deleted": N, "matches_anonymized": M}` 가 나오면 끝이다. 서비스가 떠 있어도 된다.
5. **확인과 답장**: `show <계정 ID>` 가 "그런 계정이 없다"를 내는지 본다. 요청자에게 "삭제했다, 백업에서는 최대 14일 안에 순환되어 사라진다, 앱에 남은 토큰으로 다시 접속하면 새 계정이 만들어지니 앱 데이터도 지우길 권한다"고 답한다. **삭제 요청 메일과 처리 날짜는 운영자가 보관한다** (서비스는 삭제한 사람의 ID/닉네임을 기록하지 않는다).
6. 차단된 계정도 삭제 요청으로 지울 수 있다 (다시 접속하면 새 계정이 생기므로 차단은 풀린다). 부정 이용 때문에 차단한 계정의 삭제 요청은 운영자가 판단한다.

## 5. 이 작업이 확인하지 못한 것

- **실서버/실기기**: 집 Windows PC에서 `run-accounts.ps1`이 자동 정리 옵션으로 도는 것, 24시간 뒤 정기 작업이 한 번 더 도는 것(타이머는 `--tick-sec`를 줄인 실제 서비스 프로세스로만 확인), 메일 링크로 온 요청을 처리하는 운영 절차의 실제 소요 시간.
- 방침 초안(PR #65)의 표시(`[출시 전 선결]` 안내 상자)를 지우는 일은 방침 문서의 일이라 하지 않았다 (소유자가 출시 때 한다).
- OneDrive 같은 동기화 폴더에 둔 백업 사본의 보관/삭제는 이 서비스가 제어하지 못한다.
