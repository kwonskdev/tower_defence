# 이슈 처리 순서

## 1. 이슈 읽기
- `gh issue view <N> --repo <owner/repo> --json title,body,state,labels,comments`로 본문과 코멘트까지 읽는다 (`gh issue view`만 쓰면 출력이 비는 경우가 있어서 `--json`을 쓴다).
- 본문에서 **체크리스트(`- [ ]`, 보통 "완료 조건")** 를 뽑아 작업 목록으로 삼는다. 요구사항과 "결정:" 으로 적힌 것도 그대로 지킨다.
- 이슈가 가리키는 코드를 먼저 읽고, 실제 동작을 확인한 뒤에 설계한다.

## 2. 구현과 테스트
- 체크리스트 항목마다 "무엇을 하면 확인된 것인가"를 정하고 실제로 실행해서 확인한다.
- 이 프로젝트는 Godot 4.6.3으로 검증한다 (메모리 `godot-cli-run`: 새 워크트리는 `--import` 한 번, 헤드리스 스모크 테스트, 창 모드 스크린샷). UI는 가능하면 실제 마우스 이벤트로 눌러서 확인한다.
- CLAUDE.md 지시대로 실수한 부분이 없는지 주기적으로 점검한다 (diff를 다시 읽는다).
- 커밋/푸시는 사용자가 시킬 때만 한다.

## 3. 체크리스트에 체크 표시
작업과 검증이 끝나면 이슈 본문의 체크리스트를 갱신한다.

1. 항목마다 **실제로 확인한 근거**가 있는지 판단한다. 확인된 항목만 체크한다.
   - 근거 없이 체크하지 않는다. 일부만 확인했거나(예: 에뮬레이션으로만 보고 실기기는 못 봄) 불안정한 항목은 체크하지 않고 사용자에게 이유를 말하거나, 사용자가 체크하라고 하면 그때 한다.
2. 본문을 받아 해당 줄만 `- [ ]` -> `- [x]`로 바꾼다. 줄바꿈(CRLF 등)을 그대로 보존한다.
   ```
   gh issue view <N> --repo <owner/repo> --json body -q .body > body.txt   # 스크래치패드에 저장
   # 확인된 줄만 수정 (python 등으로)
   gh issue edit <N> --repo <owner/repo> --body-file body_new.txt
   ```
3. 다시 `gh issue view <N> --json body`로 읽어 체크가 제대로 들어갔는지, 다른 부분이 안 바뀌었는지 확인한다.
4. 이슈를 닫지는 않는다 (PR이 머지되거나 사용자가 시킬 때).

## 4. 보고
- 체크한 항목과 안 한 항목(이유 포함), 실행해서 확인한 것과 못 한 것을 구분해서 알린다.
- 커밋/PR이 아직이면 그렇다고 말하고, PR은 `create-pr` 스킬 순서로 만든다.
